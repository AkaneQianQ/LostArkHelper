# 从哪里开始阅读

建议先看根目录 README，再按下面顺序阅读。三端是同一业务的三个运行方式，不是三个互相调用的服务。

## 服务器版：先沿一条请求走一遍

1. `server/web/src/ark/main.tsx`：点击查询、签到或领奖后，网页请求 `/api/...`。
2. `server/service/app.py`：HTTP 路由验证来源，识别登录用户，定位用户目录，取得操作锁。
3. `server/service/import_link.py`：导入时解析官方链接，将链接字段映射为请求表单及 Cookie。没有访问分享网页。
4. `server/service/helper.py`：实际连接腾讯官方接口，校验网络/JSON/业务返回码，提供 tasks、sign_status。
5. `server/service/automation.py`：决定何时提交，领取前再查，领取后确认，构造运行结果。
6. `server/service/store.py`：保存计划与历史，通过 UNIQUE slot 防止同一分钟重复调度。
7. `server/service/auth.py`：密码哈希、会话、限流和用户目录隔离。

定时执行与网页手动执行最终复用 helper 和 automation。systemd timer 每分钟启动调度器，调度器只处理到期账号。修改网页不会自动改变系统定时器。

## Windows：重点看服务器之外增加了什么

`启动助手.vbs → background.pyw → launcher.main()`。

- VBS 让 Python 在无终端窗口的环境启动。
- background.pyw 给无窗口进程接上滚动日志，避免启动错误完全不可见。
- launcher.py 管单实例锁、本机 HTTP、随机会话、浏览器与调度线程。
- service/credentials.py 用 Windows DPAPI 加密保存游戏凭据，仅运行中解密到内存。
- service/autostart.py 操作当前用户 Run 启动项；这属于“用户登录后启动”，不是登录前的 Windows 服务。
- service/scheduler.py 代替 Linux systemd，最近的错过时间只补一次。
- service/platform_lock.py 用 msvcrt 代替 Windows 上不存在的 fcntl。
- 停止按钮调用 app 中的 REQUEST_STOP 回调，让主线程退出并等待调度线程和 HTTP 请求完成。

单实例锁防止启动两个本地服务；操作锁防止一个账号同时提交两笔操作；SQLite slot 防止同一个计划被重复调度。三者解决不同层面的重复问题。

本地版的 pending-operation.json 记录“发过但没有确认”的操作。后续先查状态，确认已完成才移除标记；否则继续阻止提交。不能把“超时”当作服务端一定没执行。

## 快捷指令：动作图就是源码

`shortcuts/source/workflow.json` 是系统动作顺序，不是普通业务 JSON 配置。

- WFWorkflowActions：按顺序执行的动作。
- WFWorkflowActionIdentifier：系统动作名，例如 downloadurl、conditional、getvalueforkey。
- UUID：动作标识；其他动作通过 OutputUUID 读取结果。
- GroupingIdentifier + WFControlFlowMode：如果/重复的分组与开始、结束。插动作不能打乱嵌套。
- WFTextTokenAttachment：一个变量引用。
- WFTextTokenString：含变量插槽的文本；插槽位置是 UTF-16 偏移，不一定等于 Python 字符数。

JSON 前部已加中文 Comment 动作，导入后可在快捷指令编辑器中阅读。具体参数较多，建议在系统编辑器配合 JSON 阅读，不要直接用全文替换数字 ID。

`build.py` 校验动作引用和控制流，生成二进制 plist，最后调用 Apple shortcuts CLI 签名。签名不是运行测试；`tests/test_workflow.py` 的模拟也不等于 iPhone 真机验证。

## 新增任务时改哪里

1. 先确认抓包接口版本、task_id、领奖 type、成功响应及领取后状态，保留脱敏证据。
2. 服务器 `service/activity.json`、Windows `service/activity.json` 加入新 ID 的映射。
3. 快捷指令更新未知任务筛选，以及该任务完整的提交前查询、提交、提交后确认分支。
4. 更新根目录 activity-manifest.json，并运行 verify_activity.py。
5. 测试 → 服务器部署/重启加载 → 快捷指令重新签名和导入 → Windows 更新代码/打包，各端分别记录状态。

activity-manifest.json 目前是核对清单，不是自动生成三个端代码的工具，改它本身不会自动新增业务分支。

## 已知差异必须保留在脑中

服务器线上 automation 在某笔操作异常后仍可能继续后续候选；Windows 已改为停止并保存 pending，手机也会停止。打包时没有悄悄修改线上逻辑。要统一该行为，需要单独实现和部署，不能只补一句注释声称已经安全停止。

服务器与 Windows 白名单含 ID 1；手机缺少该项历史验证，所以明确保留差异。不要为了“看起来一致”静默放宽。

注释版本只在此整理目录中，未部署覆盖服务器，也不会自动更新 Windows 已安装目录或手机副本。
