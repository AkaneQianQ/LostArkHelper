# 从哪里开始阅读

四端提供同一活动的不同运行方式。服务器是多用户网页服务；Windows/Linux 是单用户本机服务；iPhone 直接调用活动接口。

## 服务器的执行链

1. web/src/ark/main.tsx：工作台请求 /api 路由。
2. service/app.py：验证 Host、Origin 与登录身份，定位账号目录并取得操作锁。
3. service/import_link.py：从用户给出的官方活动链接提取请求参数。
4. service/helper.py：请求腾讯接口，验证网络、JSON 和业务返回码。
5. service/automation.py：查询签到/任务、执行签到、刷新任务、逐项领取并确认。
6. service/store.py：计划与历史；SQLite slot 唯一约束防止重复调度，连接显式关闭。
7. service/auth.py：密码哈希、会话、限流及账号目录隔离。

systemd timer 每分钟启动调度器，只有计划到期的账号执行。server/service/activity.json 保存支持任务；verified_claims 是历史兼容字段名，6–11的推断证据由 inferred_task_ids 标明，不可误读为已实测。

## 本地版增加的部分

Windows：启动助手.vbs → background.pyw → launcher.main；打包后双击 LostArkHelper.exe。Linux：start.sh → LostArkHelper，或由 systemd 用户服务启动。

launcher.py 管理单实例锁、仅本机HTTP、随机会话、浏览器与调度线程。credentials.py 管理凭据加密：Windows DPAPI；Linux 当前用户的私有密钥文件。autostart.py 管理登录自启，scheduler.py 在进程内执行计划。停止操作等待请求及工作线程结束。

单实例锁防止多个本地服务，操作锁防止账号操作并发，SQLite slot 防止计划重复。pending-operation.json 在提交前落盘，确认成功后移除；结果未知时保留并阻止盲目重试。不同端之间没有共享锁。

## iPhone 动作图

shortcuts/source/workflow.json 是唯一源码，WFWorkflowActions 是动作顺序；UUID/OutputUUID 表示数据引用；GroupingIdentifier/WFControlFlowMode 表示条件和重复嵌套。WFTextTokenString 变量插槽使用 UTF-16 偏移。

build.py 检查引用、控制流并生成 plist，最后用 Apple CLI 签名。签名不是执行测试；模拟器也不能替代手机实测。不要运行 tools/history 中的历史补丁。

## 新增任务的顺序

1. 记录版本、task_id、领取type以及证据；推断项明确标注，成功抓包后再更新证据说明。
2. 同步 server/windows/linux 的 service/activity.json。
3. 同步 iPhone 的未知任务筛选、完整提交前查询、提交及提交后确认分支。
4. 更新 activity-manifest.json，执行 verify_activity.py 和各端测试。
5. 构建原生本地版、签名手机文件、部署服务器、发布压缩包，记录实际验证范围。

仅修改清单不会自动生成四端业务代码。活动2611现支持1–13，6–11仍为推断；不能把接口接入等同于自动完成任务条件。
